## 4. Lifecycle, succession, transfer and activation

**F-P03 proposed state machine:** workforce ACTIVE/INACTIVE remains the existing scheduling domain. A separate server-owned portal state is DISABLED → PROOF_PENDING → ENABLED, or SUSPENDED; it is not inferred from password absence or the workforce active flag. Proof provenance is distinct: existing accounts retain current credentials/access and are marked LEGACY_UNVERIFIED, never retrospectively identity-verified. New provisioning/import starts workforce ACTIVE as explicitly confirmed and portal DISABLED. Authorization incarnation/version is monotone; exact DDL representation is assigned to the schema writer at F10.01.

**F-P04 proposed activation:** a current independent authorized verifier confirms the employment, and the subject proves possession of the registered approved recovery channel. A cryptographically random digest-stored, single-use 15-minute claim binds tenant, subject, verifier, method, incarnation, purpose and expiry. Assisted no-channel verification requires a documented workplace/ownership procedure and attestation, never knowledge of employee number plus phone. No self-verification; Manager cannot verify Owner. The first Owner has no existing PortalProof: the separately authorized initial-Owner control-plane verification path below supplies the independent verifier boundary, never automatic bootstrap access. Claim consumption, credentials, portal transition and restricted audit metadata commit atomically. Generic feedback, approved cost/attempt limits and safe lost-response receipt apply. Fake channels/fictional proofs only in developer fixtures; real accounts require separate owner activation authority and retained UX-02/G3 independent/edge evidence.

DISABLED/PROOF_PENDING cannot obtain portal sessions, ordinary password-recovery activation, calendar credentials or push enrollment. The present active/no-password ID+phone route must enforce this gate on the server. F8 Finish and F9 Commit do not issue claims, credentials, invitations, PINs, sessions or delivery intents. An Owner action alone without selected identity proof cannot activate an unverified employee.

Employment deactivation suspends portal access, consumes outstanding activation/recovery proofs, revokes sessions and permanent calendar/device/PIN authority as applicable, detaches push generations and cancels obsolete unsent jobs through existing canonical policies. Record/history IDs, actual time, payroll, communications receipts and published revisions remain. Employment restore preserves portal DISABLED/SUSPENDED until a deliberate permitted verified re-enable; never reconstruct prior sessions/proofs/tokens or obsolete password material. An already verified enabled-account re-enable still requires current authority and fresh access generation. Previously revoked calendar/device/PIN credentials require their own new approved issuance.

Workspace ACTIVE/SUSPENDED is a proposed tenant lifecycle. Current Owner can deliberately suspend after impact/reason review; sessions/capabilities are revoked, ordinary private reads denied and unsent deliveries suppressed. Restore requires the narrow controlled provisioner following an authorized Owner request. Customer Owner never becomes a platform administrator. Location/position/catalog ACTIVE/INACTIVE retains stable identity/history; inactivation prevents new use. Restore permits future configured use without reviving stale feed scope/delivery intent.

A usable Owner is active employment + ENABLED access in an active workspace with current Owner authority. Owner may promote a same-tenant usable verified member through deliberate reviewed grants. An unactivated proposed Owner does not satisfy succession. Concurrent employment/portal-level demotion/deactivation/suspension of the final usable Owner must fail under tenant-local locking. Explicit whole-workspace suspension is a distinct reviewed operation: retain Owner membership/history while denying ordinary access, and use the controlled recovery purpose below rather than this employee-level guard. Legitimate self-demotion/deactivation uses narrowly captured transaction authority; after commit new actions use new rights and the old session terminates when required. Protected outcome lookup after response loss returns only its permitted safe receipt.

Within-tenant reassignment preserves employment identity. Frozen E2 grants never expand; new location eligibility requires future deliberate redistribution, not reinterpretation of old acknowledgements. E3 location loss permanently revokes affected issuance; restored eligibility cannot revive it. Cross-tenant transfer creates a new employment/internal ID and tenant-local credential boundary with separately valid authority in the destination; historical source facts remain in the original tenant. Same contact data never proves linkage. Same-tenant rehire uses explicit F7 restore of the existing record and retains its number, not CSV merge or number reuse. Historic assignments are corrected by canonical append-only commands, never removal of records.

Acceptance **F7-P01–P04**: complete lifecycle effects and historical hash continuity; last-usable-Owner concurrent changes/captured self-change recovery; rehire/transfer without reattribution or token resurrection; ACTIVE+DISABLED import cannot activate by old ID+phone, tampered claims or Finish/Commit. Capability allow/deny/legacy scope/grant ceiling cells use **F6-P01–P03**.

## 6. F8 guided Owner setup

Proposed steps, each backed by existing canonical services:

1. **Workspace:** explicit name/timezone, selected tenant shown. Timezone is configurable before operational records; afterward show existing conversion lock and recovery explanation, never a hidden conversion.
2. **Locations and positions:** create actual customer catalog values with stable codes; no Fuel seed IDs, assumed opening hours, assigned qualifications or staffing defaults. First location remains NEEDS_SETUP until its real rules are configured.
3. **Team and authority:** add employee records individually or via approved CSV. Show employee number, role, scheduling eligibility and **Portal access: Not enabled** separately. Owner/Manager custom scope and succession rules are deliberate operations; existing Owner recovery route is not an identity shortcut.
4. **Scheduling readiness:** explicit coverage periods, staffing/lead/position rules, employee availability/hour goals and existing scheduling inputs. Missing values are named; no accidental all-zero defaults that imply complete coverage.
5. **Review setup:** summary of complete/incomplete steps, remaining decisions, authorized next link to a draft schedule. “Finish setup” records setup progress only. It does not publish, activate, acknowledge, issue calendar credentials, enroll devices or send providers.

Proposed default: no mandatory tour, no wizard-only duplicate editor, and no artificial requirement that all catalog/optional features be configured. Show completion by required currently selected customer workflow, with optional skipped steps labeled. Resume from current authoritative data/version, not unchecked stored checkbox state. Configuration changes invalidate affected completion indicators. Current devices/calendar/provider readiness are separately labeled unverified/unconfigured, never included in an overall launch-ready badge.

**F8-P01:** a first-time Owner can save/resume and reach each canonical editor without reentering already saved data. **F8-P02:** refresh/back/deep link/current-source drift preserves safe progress or gives clear conflict; denied step grants no authority. **F8-P03:** empty/loading/error/success/incomplete states convey correct next action. **F8-P04:** Finish causes only progress metadata and no account/schedule/provider/capability effects. **F8-P05:** keyboard and supported mobile widths complete the required journey with visible focus and unobscured primary action.

## 7. F9 atomic create-only mapped CSV — detailed proposal

**Approved commitment mode:** one explicitly previewed bounded batch is all-or-none, create-only. Invalid/conflicting rows prevent the complete batch from committing. No silent chunking, upsert, merge, inactive restore, role update or per-row partial success. A smaller batch requires a new visible preview/confirmation. A retry of a committed operation returns its receipt, not a second creation.
