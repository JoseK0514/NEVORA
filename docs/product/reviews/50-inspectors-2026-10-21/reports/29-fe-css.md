# 29 CSS Architect — the stylesheet stack under src/app

**Verdict.** The CSS works, but it is held together by a specificity arms race. Each new design wave won by adding weight, never by replacing what came before: `.x.x` doubling, then `:not(.cm-a)`×4 padding, then `:not(#nv-kit)`, then `:not(#cm-sheet):not(#cm-sheet2):not(#cm-sheet3)`. Every `/app` page now ships about 1.6 MB of render-blocking CSS (211 KB gzip). An estimated 28% of its rules match no markup that still exists. The team's earlier `@layer` attempt failed because it layered the *oldest* files. The safe route is the reverse, plus deleting dead CSS first, and every step can be checked for zero diff with the team's existing `style-snapshot` tool.

The comments document the arms race itself. premium-wave-b.css:5 says the "seven-fold class (0,7,0) outranks … mobile-workforce.css at 0,4,3; portal-premium.css at 0,6,2". premium-wave-c.css:5 doubles a class to beat 0,7,3. premium-clean-manager.css:4 says the prefix "is long on purpose … must win without !important". The ID hack has now leaked into CSS modules too: `timecards.module.css:222`, `employee-home-reviewed.module.css:42` use `:global(...)` plus `:not(#nv-kit)`, which removes the isolation that modules exist to provide.

**Dead CSS estimate.** A rule counts as dead when every one of its selectors names a class that appears nowhere in `src/**/*.{ts,tsx,js,mjs}`. On that test, 3,312 rules (~410 KB) are dead. Biggest: globals.css 1,930/2,986 rules (~220 KB, e.g. `.metric-grid`, `.staffing-row`, `.request-card`). manager-home-gusto.css 238/260 rules: its root `.manager-portal-home` is rendered nowhere. manager-home-mobile.css 92/94. manager-schedule.css 170/234 (`.mws-header`, `.schedule-operations-shell` are gone). request-hub.css 44/67 (`request-hub-heading`). time-off.css 56/137 (`nto-*`). exchange-review.css 44/106. updates-review.css 51/115. availability.css 62/166. I spot-checked these with grep. Class names built at runtime would escape this test, so treat it as an upper-bound candidate list, not a delete list.

**Brittle coupling.** 255+ selectors target CSS-module *generated* names by substring: `[class*="notification-inbox-module"]` ×131, `[class*="__managerRoot"]` ×54, `[class*="timecards-module"]` ×49, `payroll-export-module` ×31 (portal-premium.css 145, premium-clean-manager.css 40, clean-manager/notifications.css 23). They depend on Turbopack's private `name-module__hash__local` naming scheme. If a Next or bundler upgrade changes that scheme, they stop matching with no error.

## Recommendations

1. **Ratchet first: stop the arms race growing.** Add stylelint (none exists) with `selector-max-id: 0`, `selector-max-specificity`, `declaration-no-important`, and a ban on `:not(#` and repeated-class selectors. Apply it to new and changed lines only. Add a small CI count check (`:not(#` = 286, `!important` = 268, prefix count = 1,499) that may only go down. *Why:* every QA round in Oct 18–20 added more `#cm-*` IDs: 12 fake IDs exist, and schedule.css:384 already stacks three. *Impact* High · *Effort* S · *Owner* UI.

2. **Make the U10 computed-style snapshot the gate for every CSS refactor.** `scripts/dev/style-snapshot.mjs` already snapshots 38 properties on 96 views and has a measured noise baseline (DESIGN.MD:784). Wire it as `npm run css:snapshot` and diff it before and after each step below. Add v3 Manager states (sheets, popovers, skeletons, text-step 125/150/200) to its plan, because the `#cm-sheet`/`#cm-skel` hacks live there. *Why:* nothing here can be checked by reading code. *Impact* High · *Effort* S–M · *Owner* UI.

3. **Delete dead CSS, starting with whole orphaned files.** Take candidates from runtime coverage, not grep: Playwright `page.coverage.startCSSCoverage()` over the snapshot plan, then intersect with the static list above. Start with manager-home.css, manager-home-mobile.css and manager-home-gusto.css (81 KB, root class unrendered), then manager-schedule.css, request-hub.css, the `nto-*` block of time-off.css, and the dead ~60% of globals.css. *Why:* dead rules cannot flip anything when deleted, so this step should be zero-diff. It also shrinks the set of rules that could flip in step 5. This is the "retire legacy page by page" plan that DESIGN.MD:787 already recommends. *Impact* High (~400 KB raw, faster style recalc on low-end phones) · *Effort* M · *Owner* UI.

4. **Fold the clean-manager prefix into one nested block per file (zero-diff).** Write `html body .app-shell…:not(.cm-d) { .nv-avatar {…} .nv-status {…} }` once per file. Nesting with a single parent selector keeps exactly the same specificity. lightningcss flattens it for Next's Safari 16.4 target, so the output is identical. The source drops ~183 KB and the prefix lives in one place per file, ready to shrink in step 6. *Why:* 1,499 copy-pasted prefixes; the "generated" file has no generator in the repo, so it is hand-maintained. *Impact* Medium · *Effort* S · *Owner* UI.

5. **Layer the *old* stack as one block and leave v3 on top.** This inverts the attempt that failed in U10. Declare `@layer legacy, v3;` as the first statement of globals.css. Wrap **every** non-v3 sheet in `@layer legacy {}`: root sheets, portal-*, kit, premium-*, page CSS **and CSS modules**. Because they all share one layer, their cascade among themselves is unchanged. U10 broke by layering only 6 files, which let dormant module CSS win (18,033 diffs). v3 rules match only under `[data-nv-clean]`, so Employee and Lead pages are untouched by construction. On Owner and Manager pages, the only possible diffs are v3 declarations that currently *lose* to an ID-weighted legacy rule. Those are dead today: delete them or accept them, one by one. `!important` is safe: v3 has none, and legacy `!important` still beats v3 normal declarations, exactly as today. *Impact* High · *Effort* M · *Owner* UI.

6. **After step 5, strip the weight hacks.** Shorten the v3 prefix to `.app-shell[data-nv-clean]`. That is a uniform subtraction, so the order of v3 rules among themselves is preserved. Remove each `:not(#cm-*)`, keeping one only where the snapshot shows it beats another v3 rule. Then remove `:not(#nv-kit)`/`:not(.nv-shell-none)` and the `:global` hacks inside legacy as those pages are retired. *Why:* the cascade becomes layer order plus at most 0,3,0 specificity, which is readable again. *Impact* High · *Effort* M · *Owner* UI.

7. **Replace the substring selectors on module class names.** Give module roots and parts stable hooks (`data-part="inbox-title"` or a plain global class next to `styles.x`), then select on those. Alternatively, move the override into the module itself. Start with notification-inbox (131 selectors) and timecards (`__managerRoot`, 54). *Why:* 255+ selectors depend on bundler-private class naming, and no test guards them. *Impact* Medium (silent breakage risk on upgrade) · *Effort* M · *Owner* UI.

8. **Split CSS by audience: stop shipping app CSS to sign-in and v3 CSS to employees.** globals.css (372 KB) loads on `/login`, `/activate`, `/forgot-access` and `/reset-access`. Move portal rules into the `/app` layout so auth pages get only tokens, reset and auth CSS. Inside `/app`, the 401 KB v3 stack loads for Employees but matches nothing for them. Once the legacy stack is retired (step 3), v3 page sheets can move to per-page imports, like `clean-manager/schedule.css` → schedule page. *Why:* render-blocking CSS on the first visit, and the auth screens are the first impression. *Impact* Medium · *Effort* M · *Owner* UI.

9. **Collapse the token families and reconnect the v3 tint to the brand chain.** 792 custom properties across `--nv`, `--g`, `--design`, `--cm`, `--corporate`, `--mobile`, `--mh`, `--nevora`, `--nuvora`… and 30 different `*accent*` names. v3 hard-codes `--cm-tint: #087571` and maps `--nv-accent` to it (premium-clean-manager.css:8,14). It never reads `--g-accent`, which `derive.ts`/the shell inject per company (app-shell.tsx:211). Owner/Manager v3 surfaces therefore ignore a workspace's custom brand colour, and the base teal now exists as two near-identical values (#077572 vs #087571). Define one semantic tier (`--color-accent`, `--color-label-2`…) that v3 and kit both read, aliased to `--g-*`. *Impact* Medium · *Effort* M · *Owner* UI (Product to confirm whether v3 should honour company colour).

10. **Stop opening a new global sheet for each parallel session.** The Oct 19 pattern of one file per session (wave-a/b/c, desktop, profile), each using "the same high-specificity prefix", is what multiplied the conflicts: `.mobile-header` is styled in 11 files. New work should land in the kit (`kit.css` is clean: average 1.4 classes, max 0,4,0) or in the page's own module/sheet inside the v3 layer. Add one rule to TEAM-RULES: "a component's base look is owned by one file". *Impact* Medium · *Effort* S · *Owner* Product + UI.

## What's good
- `src/components/kit/kit.css` is a sane base: low specificity (max 0,4,0), 2 `!important`, tokenised. It is the right target to grow into.
- The team built a real regression oracle (U10 computed-style snapshot with a noise baseline) and honestly measured and reverted a bad `@layer` attempt. Most toolkits lack either.
- The v3 scoping by `data-nv-clean` is consistent, with no `!important` in the whole v3 stack. That is what makes recommendations 5–6 provably safe for Employee pages.

## Not checked / limits
- No browser (per brief): I did not measure runtime CSS coverage, style-recalc cost or real chunk order. The dead-rule numbers come from a static class-name test and are an upper bound; runtime-built class names may hide some live rules.
- Specificity figures come from a regex scorer that counts all `:is()`/`:not()` arguments, so maxima for `:is(#a,#b)` lists are overstated. The quoted examples were checked by hand.
- I did not verify whether Turbopack production builds keep the `-module__` naming that 255+ selectors rely on, or whether dev and prod CSS chunk order match.
- I did not run style-snapshot, so none of the migration steps has been measured. Each needs its own snapshot diff before merge.
