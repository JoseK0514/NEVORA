# 27 Internationalization Engineer — readiness to ship NEVORA fully in Puerto Rico Spanish

## Verdict
NEVORA is not ready for a Spanish release. Outside the Clocker's second-line labels and the payroll PDF statements, every screen is hard-coded English. There's no message catalog, no per-person language setting, and `<html lang="en">` is fixed. Formatting is pinned to `'en-US'` in 89 places, and English-only string surgery runs after formatting. The parts already built (Clocker lines, `es` word slots, statement language, `es-PR` currency) are good seeds. The job is large but mechanical. I estimate 8–11 engineer-weeks plus translation and review, done in waves with employee pages first.

Scale, from an AST scan of 727 non-test `.ts/.tsx` files (crude, so it overcounts somewhat):
- 1,984 JSX text nodes, about 3,000 UI attributes or labels, 262 text template literals, 1,550 sentence-like strings in `src/lib`.
- Roughly 20–30k English words in all.
- About 4,000 unique messages once duplicates are removed (my estimate).

## Recommendations

1. **Adopt one i18n library with ICU messages and no locale in the URL. Recommended: `next-intl` in "without i18n routing" mode.** The locale comes from the person's saved language, then a cookie, then `Accept-Language`, then `en`.
   - **Why.**
     - There's nothing to build on today. No i18n dependency is in `package.json`, and the only dictionary is the 18-phrase `CLOCKER_ES` map (`src/components/clocker-language.tsx:9-15`).
     - The direction doc requires that "every route … stays" (`docs/product/direction.md:160`), so URL prefixes such as `/es/...` are out.
     - ICU plural and select messages are needed for the agreement problems in rec 3 and rec 4. A hand-made typed map like `CLOCKER_ES` can't express them.
     - Server components render most pages, so the library must work in RSC.
     - Check that it works with Next 16.3 / React 19.3 before adopting. Lingui is the fallback if bundle size matters.
   - **Impact:** High. **Effort:** M (foundation, about 1.5 weeks). **Owner:** UI.

2. **Add a per-person language field and make it the single source of truth.** It should drive:
   - the UI
   - `<html lang>`
   - push titles (`src/lib/notifications/payloads.ts:10-18`)
   - the recovery email (`src/lib/auth/recovery-delivery.server.ts:31`)
   - statements

   Today the only language data is the payroll statement setting (`src/components/payroll/payroll-settings.tsx:116,178`; `src/lib/payroll/documents.ts:170`). The Clocker's on/off is stored per tablet in `localStorage` (`clocker-language.tsx:18`). The layout and global error page hard-code `lang="en"` (`src/app/layout.tsx:25`, `src/app/global-error.tsx:6`).
   - **Product decision:** should the payroll exception stay as an override, or simply follow the person's language?
   - **Impact:** High. **Effort:** M. **Owner:** Backend (column, session, payloads) + UI (Profile picker) + Product (override rule).

3. **Turn the words system into real message arguments, with grammatical gender, and stop hard-coding `.en`.**
   - **Why.**
     - Reviewed `es` slots exist (`src/lib/workspace-presentation/words.ts:10-25`), but every consumer reads `.en`. Examples: `src/app/app/layout.tsx:68`, `settings/page.tsx:78`, `employees/page.tsx:18`, `settings/locations/*.tsx`, `presentation-context.tsx:10`, `navigation.ts:141`, `finder.ts:28`, and the preset picker shows only `p.en` (`features-editor.tsx:83`).
     - The slots carry no gender, so Spanish breaks at once:
       - "this ${lower(words.location)}" (`settings/locations/[locationId]/page.tsx:24`) needs "esta tienda" but "este restaurante".
       - "All stores" needs "Todas las tiendas" but "Todos los empleados".
       - "eligible ${people}" (`settings/locations/page.tsx:99`) needs "elegibles", which agrees in number.
     - `lower()` plus English glue ("Add ${…}", `finder.ts:29`; `new-location-form.tsx:83-114`) bakes in English word order.
   - **What to do.** Add `gender: 'm'|'f'` per Spanish slot. Pass the slots as ICU arguments (`{location}`, `{locationGender, select, f {esta} other {este}}`) rather than concatenating them.
   - **Impact:** High. **Effort:** S. **Owner:** UI.

4. **Replace the hand-rolled pluralization and concatenation with ICU messages.**
   - **Why.**
     - There are 0 uses of `Intl.PluralRules`.
     - There are 7 private `plural(n, one, many)` helpers: `premium-home.tsx:54`, `manager-dashboard.tsx:130`, `manager-shift-requests.tsx:94`, `manager-weekly-roster.tsx:40`, `clean/week-summary.tsx:8`, `payroll-stepper.tsx:8`, `manager-time-off.tsx:130`.
     - There are 78 inline `n === 1 ? "x" : "y"` ternaries (for example `schedule/settings/page.tsx:123`, `owner-setup-card.tsx:13`).
     - 106 `"string" + value` concatenations also hold sentence fragments, for example `aria-label={name + " minimum staff per shift"}` at `schedule/settings/page.tsx:108-112`.
   - Spanish needs the noun, adjective and verb to agree together ("1 empleado no tiene…" / "3 empleados no tienen…"). So the sentence has to be whole, not glued from parts.
   - **Impact:** High. **Effort:** M (done as part of extraction). **Owner:** UI.

5. **Centralize date, time, number and duration formatting in one locale-aware module, and remove the English-only post-processing.**
   - **Why.**
     - There are 95 `Intl.DateTimeFormat` calls across 43 files, with `'en-US'` hard-coded 89 times.
     - Several helpers build English by hand:
       - `formatTime` builds "AM/PM" (`src/lib/date-utils.ts:69-75`)
       - `timeText` gives "midnight"/"AM" (`manager-inbox.tsx:110`)
       - `durationText` gives "8h 30m", used in 11 files (`src/lib/duration-text.ts`)
       - `timeZoneLabel` gives "Puerto Rico time" (`src/lib/time-zone-label.ts`)
       - four hard-coded English weekday arrays (`schedule/settings/page.tsx:27`, `company-policy-editor.tsx:238`, `availability-editor.tsx:17`, `availability-team-list.tsx:25`)
     - `keepWhole()` regexes match only English month and AM/PM shapes (`src/lib/keep-whole.ts:4-12`). It runs in 113 places, so in Spanish its no-break protection silently does nothing.
     - Other code patches English output after formatting: `.replace(" ", nbsp)` (`manager-time-off.tsx:29,127`) and `.replace(/ (AM|PM)$/…)` (`brand-editor.tsx:63`).
   - **What to do.** Have the formatter emit non-breaking spaces itself, using `formatToParts`.
   - **Things to know about `es-PR`, measured in Node:**
     - It gives "mié, 21 oct, 1:30 p. m." and "21 de octubre de 2026".
     - Its short time-zone name is "GMT-4", not "AST". Keep the people-facing "hora de Puerto Rico" label instead.
     - Use `es-PR`, not `es-ES`. CLDR `es-PR` keeps US-style "$1,234,567.50" and "1,234.5", which is correct for Puerto Rico. `formatPayrollMoney` already does this (`src/components/payroll/money.ts:5`).
   - **Impact:** High. **Effort:** M. **Owner:** UI.

6. **Fix the time-zone gaps now. They are bugs in English too.**
   - These calls format in the device's or server's time zone instead of the workspace zone:
     - `notification-inbox.tsx:92,143`
     - `configured-attendance-policies.tsx:15`
     - `payroll/payroll-settings.tsx:27`
     - `src/lib/notification-inbox-view.ts:11`, which groups by day and is wrong on a UTC server
   - `payroll-runs.tsx:108` uses `new Date(run.approvedAt).toLocaleString()` with no locale and no zone. That gives a server/client hydration mismatch and the wrong zone for anyone outside Puerto Rico.
   - Each one should take `workspace.timeZone`, as the other 75 calls do.
   - **Impact:** Medium. **Effort:** S. **Owner:** UI.

7. **Make every in-app search ignore accents.**
   - Puerto Rico names carry accents: "María José", "Muñoz", "Ramón".
   - The team directory already folds them (`src/lib/employee-directory.ts:8`, NFKD plus strip marks).
   - These searches don't, so "jose" doesn't find "José":
     - the ⌘K / phone finder (`src/lib/finder.ts:33-45`)
     - roster search (`src/lib/scheduling/manager-roster-presentation.ts:35`)
     - rules-hours search (`src/components/rules-hours-list.tsx:22`)
     - break-type search (`src/components/clocker-break-types.tsx:115`)
   - Move the `searchable()` helper into a shared module. Sort names with `Intl.Collator('es-PR')` rather than bare `localeCompare`.
   - **Impact:** Medium (a live usability bug today). **Effort:** S. **Owner:** UI.

8. **Before any translation, run a pseudo-locale (`en-XA`, +35% length, accented letters) through the existing 390 / 1440 / 200%-text sweep.**
   - **Why.**
     - The shared segmented control is `flex-wrap: nowrap; overflow-x: auto` with a hidden scrollbar (`src/app/app/premium-clean-manager.css:558-561`). Section tabs use `flex: 1 0 auto` (`:257`). At 390px, longer Spanish labels will push segments off-screen with no visual cue. For example, "Timecards · Payroll runs · Time exports" becomes roughly "Hojas de horas · Nóminas · Exportaciones".
     - The CSS also has 173 `white-space: nowrap` rules, 33 ellipsis rules and 46 uppercase transforms that need checking.
     - From the screenshots, the tightest spots are:
       - the 5-tab phone bar (`QAOWNER-home-390.png`: "Schedule" becomes "Horario", "Inbox" becomes "Bandeja")
       - the nav-bar trailing action ("Select" becomes "Seleccionar", `QAOWNER-timecards-390.png`)
       - right-aligned durations
   - A pseudo-locale finds these issues in a day without waiting for a translator.
   - **Impact:** High. **Effort:** S. **Owner:** UI.

9. **Return error codes, not English sentences, from the server.**
   - **Why.**
     - Server actions return 76 English `error:`/`message:` strings, for example `settings/breaks/actions.ts:12-28` and `settings/clocker/actions.ts:11-21`.
     - Payroll shows `error.code.replaceAll("_"," ").toLowerCase()` to people (`src/lib/payroll/http.ts:80`).
     - `src/lib/data`, `scheduling`, `clocker` and `action-center` hold about 650 more sentence-like strings.
   - **What to do.** The client maps each code to a message with parameters. That keeps data contracts stable while the copy is translated.
   - **Impact:** Medium. **Effort:** M. **Owner:** Backend (codes) + UI (catalog).

10. **Finish the statement language, then roll out by page and protect the scripts.**
    - **Statement fixes.**
      - The PDF prints money as "USD 1234.56", with no grouping and in both languages (`src/lib/payroll/documents.ts:16-18`).
      - Periods and paydays print as ISO dates, "2026-09-01 — 2026-09-15" (`:155-157`).
      - Fix both with the shared formatter (Helvetica WinAnsi covers the result), and get Spanish payroll and legal copy approved.
    - **Rollout order.**
      - Wave 1, Employee and Lead (Lead shares the employee pages): shell and nav, Home, My schedule, My time / Timecards, Requests hub (time off, shift requests, availability), Updates, Notifications, My pay and statements, Profile with the language picker, push and email.
      - Wave 2, Manager daily: Today, Inbox, Schedule, Timecards, Team.
      - Wave 3, Owner: Settings, Payroll, Insights, exports, setup. These carry the most legal and payroll text.
    - **Protect the scripts.** 1,368 `getByRole/Text/Label` selectors across 35 script and test files press English names, and the Clocker keeps English `aria-label`s on purpose. So:
      - pin `en` as the test default
      - add a Spanish run of the 156-check sweep
      - add an ESLint "no literal strings" ratchet so new screens can't add English
    - **Impact:** High. **Effort:** L in total. **Owner:** UI + Product (legal copy, release slot after the moved prod release).

## What's good
- The Clocker's bilingual lines are carefully accessible: a separate `lang="es"` element, hidden inside buttons, with English names kept for scripts (`clocker-language.tsx`, DESIGN.MD U9). That's the right pattern to grow from.
- The vocabulary presets ship reviewed Puerto Rico Spanish forms, and the statement language with a per-employee exception already works end to end in the PDFs.
- Currency is integer-safe and uses `es-PR` correctly (`money.ts`). 75 of 80 date calls already take the workspace time zone, and the directory search already folds accents.

## Not checked / limits
- I used no browser, per the brief, so expansion risks are inferred from CSS and the 390/1440 screenshots, not measured in Spanish.
- String counts come from a heuristic AST scan. They include some non-UI strings and miss strings built at runtime. Unique-message and word totals are estimates.
- I didn't verify `next-intl` against Next 16.3 / React 19.3. I didn't review Spanish legal or payroll wording, the Clocker kiosk copy beyond its dictionary, or the PWA manifest and app-shortcut labels (`notifications/manifest.ts`).
