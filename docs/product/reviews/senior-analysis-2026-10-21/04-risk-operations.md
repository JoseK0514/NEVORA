# Engineering and operational risk review — October 21, 2026

**Lens:** senior business analyst, technical and operational risk. What in the engineering setup could hurt a real customer or the launch, written for Jose.
**Scope read:** CI workflow, package scripts, database migrations, auth/PIN/session code, the Clocker punch and recovery path, payroll document access, the notification worker, deploy configuration, the browser QA harness, and the release-control documents. Branch `claude/auth-premium` (draft PR #17 into `development`) was read as the newest UI-plus-backend merge. This is a sample, not a line-by-line audit.

**Where things stand today:** `development`'s CI has been red since October 20. The direct cause is small — `src/lib/company-access/operational-scope.server.ts` imports a package called `server-only` that was never added to `package.json`, and since backend commit c57c89c3 that file is pulled into test scripts that run outside Next.js, which is the only place the import works. Three CI jobs fail on it (release-postgres, phase-d-attendance-ui, phase-e-ui). Two more failures are unrelated: an inbox-authority test in phase-e-postgres and `src/test/notification-worker-startup.test.ts` in validate. PR #17 inherits all five; it changes none of those files. (Evidence: side-session note `pr17-ci-2026-10-21.md`, runs 39409730347 / 39421267504 / 39427239840.)

## Pre-launch checklist — do, or explicitly accept in writing, before the first real customer's data

1. **Green CI on the exact release SHA.** Codex declares `server-only` (one line plus lockfile) and fixes or formally quarantines the inbox-authority and worker-startup failures. No deploy without the green run's URL in the release note. (R1, R2, R6)
2. **Treat the inbox-authority failure as a privacy question until answered.** It asserts management inbox access control and currently resolves the wrong way. Codex states whether product code or the test is wrong. (R6)
3. **Migration hygiene.** Unique numbers (or a runner with a ledger); a written statement of what production has applied; one dry run of the full chain on a fresh database *and* as an upgrade from a copy of production's current state. (R3)
4. **Rollback rehearsal.** Redeploy the previous Vercel build against the migrated database once, and confirm the app works — turning the release note's "a normal rollback keeps it" from a claim into a tested fact. (R3, R7)
5. **Minimum observability.** Health route, external uptime alert to Jose, error tracking wired in, one timed Neon restore drill with notes. (R4)
6. **Workers scheduled and proven.** Cron (or equivalent) calling the internal worker routes, one end-to-end run on hosted Preview showing a reminder and a payroll document actually produced. (R5)
7. **FR-AUTH-001 closed or excepted.** Codex's independent review of the authorization corrections on the final SHA, or Jose's signed exception. (R7)
8. **Hosted load check at launch size.** Measure Manager Schedule and inbox on real Neon with the launch customer's realistic headcount; set a number that is acceptable. 10.6 seconds is not, at 200 people. (R7)
9. **Support runbooks** (see list below) — at least "site down", "internet down at the venue", "punch missing/duplicated", "restore from backup". (R4, R8)
10. **Shared-device session decision.** Keep or shorten the 14-day portal session for management roles on tablets; write the guidance either way. (R9)

## Missing operational artifacts (each absence verified in the repo)

- Production migration **runner** and an **applied-migrations ledger** table — nothing records what the live schema has.
- **Health-check endpoint** — none under `src/app/api/`.
- **Error tracking / log drain** — no such dependency or config anywhere.
- **Uptime monitoring and alerting** — none.
- **Backup and restore policy, and any record of a restore drill** — none (Neon presumably snapshots; untested here).
- **Scheduler for the notification and payroll workers** — no crons in `vercel.json`, nothing else in-repo.
- **Incident-response / support runbooks** — none (the closest are phase checkpoints, which are release documents, not operations documents).
- **Rollback procedure document** — one sentence in a release note is the only trace.
- **On-call / escalation note** — implicitly "Jose", written nowhere.
- **Staging definition** — "hosted Preview + isolated Neon" is practiced per-release but not written as a standing environment.
- **SLO or uptime target** — none; for a time clock, "available at shift boundaries" is the business-critical window.
- **Secrets inventory and rotation procedure** — env names are discoverable in code (`DATABASE_URL`, `NEVORA_CLOCKER_PIN_KEY`, `PUSH_VAPID_PUBLIC_KEY`/`PRIVATE_KEY`, `PUSH_SUBSCRIPTION_ENCRYPTION_KEY`, the worker bearer secret), but there is no document saying where each lives, who can read it, or how to rotate it. No secret values are committed, which is right.
- **Branch protection** — unavailable on the current GitHub plan; the written procedural controls are the compensating control and should stay mandatory.
