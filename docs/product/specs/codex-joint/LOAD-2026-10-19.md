Source: `80081b1` for the baseline; the rerun adds only the bounded owned-transport pool patch (file hashes retained in each runtime manifest). Real Next production build/start, actual authenticated HTTP, fresh owned PostgreSQL 17.11 cluster per run. This substitutes the DB transport and refuses tenant-runtime access; it does **not** exercise hosted Neon, Vercel, tenancy-runtime routes, WAN latency or production limits. Four CPU quota, same machine, sequential runs. No hosted database/notification provider was used.

Fictional seed: exactly 200 employees including Owner/Manager, long names, 350 published shifts (50/day this week), 4,015 closed entries (365 per each of 11 employees), reviewed fictional rules and location/position eligibility. Each surface had one excluded warmup followed by 40 requests at concurrency 10 and 40 at concurrency 20. Groups run separately, not as a mixed-user traffic model. Times are complete HTTP body latency in milliseconds (nearest-rank p50/p95), not browser paint times.

Baseline had **205 failed/degraded responses out of 880**; the pooled rerun had **880/880 successful complete responses, no unavailable snapshots or rendered failures, and no HTTP timeouts**. All JSON outcomes were `state:ready`; HTTP 200 alone was not treated as success. Baseline failures were Home manager 61/80, Inbox 75/80, inbox-count 69/80. That includes rendered-error HTTP 200s and unavailable-count HTTP 200s. The baseline server log contains actual PostgreSQL `53300` (too many clients) and the masked “Workspace configuration is unavailable” errors. No statement timeout was observed in this workload.

**Smallest local fix:** `src/test/integration/owned-pg-transport.ts` now uses one pool per transport with maximum 12 connections, retaining 3-second connection/acquisition timeout and 5-second statement timeout. Ownership name/OID/comment is checked at every checkout; transactions stay on one connection; aborted work destroys its connection. Idle connections expire after one second and callers can close the transport. No production module imports this test-only transport. Apply the change in the main checkout only at a chat round break, then restart that chat’s own runtime; do not hot-edit imports during a frozen inspection. This does not centrally budget six separate preview pools; watch total local DB/process resources as well.

**Production assessment:** the local connection-per-query fan-out is not the production Neon HTTP transport. `getWorkspace()` masks *any* storage/validation error behind “Workspace configuration is unavailable”, so the same message can still occur in production if Neon fails, rate-limits, times out, or returns invalid configuration. It is not evidence that configuration rows disappeared. Keep this read fail-closed: do not substitute an invented timezone or stale authority/configuration. Production scheduling mutation guards explicitly set 1.5-second lock and 5-second statement timeouts; database/provider request limits can also affect reads. None of those production limits was removed or raised.

**Open performance risk for Jose/Claude:** Manager Schedule p95 is **10.6 seconds at concurrency 20**, even after connection failures are fixed. This is full HTML/server rendering of 200 employees/350 shifts, not an isolated SQL timing. Schedule combines generation review, captured positions, roster construction and React rendering. Needs backend CPU/query profiling plus UI payload/render review before asserting a production SLO. Inbox-count p95 is **3.0 seconds** because it recomputes the full authorized action center; avoid overlapping browser refreshes and do not request it repeatedly per component. A request-scoped shared read or lighter exact count projection needs contract/authority regression tests; no cross-session cache was introduced. Hosted Neon latency, pooler limits, cold starts and actual deployment size remain unmeasured, so this is not production capacity certification.

**Indexes:** existing indexes include sessions token PK/employee/expiry, shifts employee/date and schedule/date, schedule location/week unique, time_entries employee/clock_in_at DESC, break_entries time-entry history, and timecard revision employee/period. Actual `EXPLAIN (ANALYZE,BUFFERS)` of employee recent-time lookup used `time_entries_employee_history` and ran in 0.043 ms. No missing index is demonstrated by this probe. Complete source-snapshot JSON aggregation and large server projections cannot be fixed by adding an arbitrary index. Full main-query plans/hosted slow-query evidence are a remaining profiling gate, rather than a claim that every query is optimally indexed.
