# Native platform capabilities

Local implementation under the approved November1 native design. The direct WKWebView/Android WebView hosts the existing server-authorized Employee/Owner portal. Browser cookies stay in the browser; native capabilities never export cookies, provider tokens or private keys.

The version1 channel `nevoraCapabilities` admits only the configured HTTPS origin's main frame and a currently ready page. Messages have exactly `version`, `id`, `nonce`, `method`, `payload`; allowed methods are hello, notifications.permission, notifications.complete and notifications.detach. A new page/lifecycle retires pending replies and native IO. Limits are16KiB envelope,8KiB payload,64IDs/page and8second native IO; invalid/replayed/foreign-frame messages fail closed. Hello returns public SPKI/fingerprint, nonce, permission, active generation, installation revision and a maintenance-busy flag only. A detached revision is not an active generation. The web adapter requires both current authenticated server status and matching native generation before displaying alerts on. Turn off carries the reviewed generation. Successful detach returns a new tombstone revision; retain it for later enrollment, without displaying it as active.

Permissions alone never enroll. A deliberate action obtains a fresh browser-session enrollment challenge; native validates its scope,120second lifetime and canonical proof bytes, signs using an installation-scoped nonexportable P256 key, and completes through the fixed cookie-free endpoint. Tokens remain native. Unchanged tokens do not rotate; token callbacks fence older cached SDK results. Rotation/detach use signed generation-bound maintenance. Native-only rotation survives document retirement, retains the same server account/session/revision binding, and may persist its result only if the current active native revision still matches its starting revision. Page enrollment and user detach retire with the document. The web settings wait read-only for bounded native maintenance before claiming enrollment; they never automatically enroll a later account. Server session revocation still denies dispatch. If a committed completion reply is lost, Review app setup asks explicitly before issuing a fresh authenticated `reconcile` challenge. This captures one current installation revision, binds the current account/session and operation ID, requires the same installation key signature, and retains the existing atomic revision check. A concurrent change conflicts; ordinary enrollment with null still means no existing installation. No automatic retry adopts a newer account or revision. Public fixtures contain no real token/private key; cryptographic tests create ephemeral signing keys.

Push is disabled by default. iOS build settings: `NEVORA_BACKEND_ORIGIN`, `NEVORA_NATIVE_PUSH_ENABLED=true`, `NEVORA_NATIVE_PUSH_ENVIRONMENT=test|production`. Actual signed builds additionally need approved account/profile, the example entitlement file selected by `CODE_SIGN_ENTITLEMENTS`, `NEVORA_APS_ENVIRONMENT=development|production` matching test/production, and `NEVORA_ASSOCIATED_DOMAIN`. No entitlement/profile/account is configured here. Release installation keys require Secure Enclave; Debug simulator uses a nonexported software key.

Android Gradle properties: `nevoraBackendOrigin`, `nevoraNativePushEnabled=true`, `nevoraNativeEnvironment=test|production`, and `nevoraNativeFirebaseProject`, `nevoraNativeFirebaseApp`, `nevoraNativeFirebaseApiKey`, `nevoraNativeFirebaseSender`. These are public Firebase application identifiers, not server service-account credentials. Firebase initialization/token acquisition requires explicit native configuration and notification permission; automatic initialization, analytics and delivery-metrics export are disabled. Keystore private material never leaves native storage. Default builds do not request a token or call a provider. Server registration/delivery gates remain separately configured as documented in native-enrollment-protocol.md and native-dispatch.md.

Incoming HTTPS links admit bounded exact-origin portal/auth routes, reject ambiguous encoded/dot paths, fragments and duplicate query keys, and wait for fresh protected navigation. Generic notification IDs/generations go to the existing authorized open route only when native generation matches. The server rechecks recipient authority. Association examples under native/association need real domain, team/package and signed certificate before controlled deployment; none is deployed. Passkey/association behavior requires Phase3 HTTPS/physical evidence.

Documents currently use an explicit browser reauthentication/download flow from known payroll/report destinations. The app never copies cookies, appends bearer credentials, fetches private files through arbitrary native URLs or persists shared private files. This is a deliberate safe fallback; native file preview/share is not qualified. Android POST/blob requests cannot be replayed safely by copying browser cookies. Browser login and the existing authorized document operation must be performed again. Known document GETs are intercepted before PDF/JSON rendering. Owner exports and period-close artifacts return to `/app/payroll-export`; shared payroll document routes use only the current known `/app/my-pay` or `/app/payroll` context. Unknown context returns through `/app` for server role routing. This memory-only context contains no document identifiers or query parameters and retires with the native lifecycle.

Builds/core tests, real local backend journeys, hosted/device acceptance and signed distribution are separate evidence. Phase1's intermittent older-WebView accessibility defect remains open until its cause/correction is established. Local Phase2 verification and whole-change review are tracked in evidence/2026-11-04/phases-1-2/progress.md. No production/account/provider action, signing, upload, merge or push is implied.
