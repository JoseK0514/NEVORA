The Requests page checks the workplace Time off module before reading the authenticated employee’s requests. Reads do not require mutation proof. Creation and withdrawal separately require the current self-service role, module and server proof. Self-service admits Employee/Lead; management review is separate. Withdrawal targets a current own Pending request, with an identical own cancellation replay permitted. Receipts require a returned result. Availability and the Requests hub remain independently available.

Creation validates a UUID v4, ordered valid dates, and same-day partial hours with end after start. The prototype preserves its earlier “sample today or later” constraint; that is not a new source-server rule. Source idempotency accepts only an identical own original request. The local model checks current owner/workspace/sample session, module, read freshness, proof, generation and original payload at review/send/cancel. Home and notification projections use the same own Time off visibility. Notification suppression follows the module’s declared policy; the exact live notification path was not verified here.

The source form retains a module-memory draft keyed by employee ID, but clears it before sending and does not retain a UUID or offer explicit discard. This prototype intentionally strengthens that behavior: root-memory draft ownership includes employee/workspace/sample session; dismissal and navigation retain fields/UUID; confirmed local success or confirmed discard clears them; sign-out clears all Time off state. Temporary same-owner read/module/proof failure withholds private editing while retaining the draft. Owner loss clears or withholds it. Refresh resets all sample memory. No private browser persistence was added.

The failed-send fixture represents a known pre-send failure. It retains the identical draft and requires deliberate retry. Real unknown network outcomes, durable idempotency, server authorization, session revocation and concurrency still require application integration and separate verification. The browser prototype is not an authorization boundary.
