## Production-build browser runs: harness limits, not app regressions
- **WebKit loses the session over plain http.** In production, `src/lib/auth/session.ts:51` sets the session cookie
  `secure`. Chromium keeps secure cookies on `http://127.0.0.1`; WebKit drops them. Sign-in reaches `/app`, then
  `/app/schedule/edit` shows the sign-in page (`webkit-UI-COMPANY-failure.png`). Only an https origin can fix this:
  the owned TLS proxy (`src/test/integration/owned-tls-proxy.ts`), the way the Clocker production run does. The app is
  correct to set `secure`.
- **Concurrency test vs production prefetch.** The test counts every RSC GET to `/app`, `/app/schedule` and
  `/app/schedule/edit` as a pending router read and waits up to 20 s for it to finish. Production builds prefetch
  links; a `/app/schedule` RSC read got its 200 response but never finished within 20 s, and the page then showed
  "Couldn't open that shift". Development builds don't prefetch, and the test passes there. The test's drain rule
  needs to ignore prefetch reads (`next-router-prefetch` header) before it can run on a production build.
- The 2 WebKit console errors recorded in the production run ("…/app/timecards?_rsc=… due to access control checks")
  are aborted prefetches during navigation, the same family as G69. The development-build WebKit run recorded none.

Until the harness is fixed, each run also does the development-build browser run, so WebKit and the concurrency
checks still catch regressions.
