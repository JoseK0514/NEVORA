# Process-observation failures under CPU load: root cause (read-only)

Revision 99e1dbe5. I read the code and the preserved logs only and ran nothing. The failure signatures come from `docs/execution/employee-mobile-device-alerts/evidence/execution/evidence/default-unit.log:1234-1281`.

## Common mechanism
All three failures report `error: "Owned resource observation failed"`. Each comes from a **check-then-act race between `ps` observations that run one after another** in `scripts/phase-e-owned.mjs`. A *legitimate* process exit lands between two reads, and the supervisor classifies the inconsistency as an observation failure. CPU load does not push `ps` past its 2 s timeout. The ps-latency probe ruled that out (max 152 ms, 0 errors; I recomputed this from `evidence/ps-latency-*.jsonl`). What load does is stretch each `spawnSync('ps')` from about 5 ms to 25–150 ms, which widens every window by roughly 10–30×. A snapshot makes about 4–6 `ps` spawns, so its duration D approaches the 250 ms poll period (`:269`). Node starts a repeating timer's clock *before* its callback runs, and the timers phase runs before the I/O phase that delivers SIGCHLD/`exit`. Once D ≈ 250 ms, a new poll can run after a child's death but before Node emits `exit`. The tests use no fake timers (verified by grep).

## 1. phase-e-process: `retained Linux marker observation: changed-member` (a) product race
- **Assertion:** `src/test/phase-e-process.test.ts:126` expects status 0 and receives 1. The receipt shows `observationFailure:{reason:"LEADER_UNPROVEN"}` with no `pid` or `phase` field, and `elapsedMs 2429` (verified, log :1235).
- **Origin:** a bare `LEADER_UNPROVEN` without pid or phase can only come from `:205` or `:244`. Teardown happened about 2.4 s in, which rules out `:244` (spawn time). So the throw is `:204-205`, the title-change branch. That branch is reached only when a member's command hash has changed (`:197`), and the worker retitles itself at 800 ms (test `:111`). This also explains why `stable-member` (same teardown, no retitle) never fails.
- **Race:** the fixture tears down normally with `process.kill(-resource.pid,'SIGKILL')` at 2000 ms (test `:113`). The snapshot (`:214`) reads the table, then the worker's identity (alive, `ppid` = leader). The group SIGKILL lands, and the leader becomes a zombie, so `processIdentity` returns undefined (`:80`). The leader re-proof at `:204` then throws. The window spans about two `ps` spawns, and load widens it.
- **Class (a):** the same thing happens in real runs whenever a Next group with a retitled `next-server` worker is torn down while a poll is running. It fails closed, so it is safe but gives a false failure.

## 2. phase-e-root-group-process: `root-exit` (a) misclassification; the test encodes event ordering
- **Assertion:** `:58` expects `'Owned child left runtime resources running'` and receives the observation failure (verified, log :1253). The reason was not preserved.
- **Race (inferred):** the snapshot that sees the worker sets `finished`, which triggers the root's exit (test driver `:36` → child `:28`). The root dies and the worker is reparented to PID 1. The next poll's snapshot then runs *before* the `exit` event (`:275`). At `:219` the root-group lease now fails `isDescendant(...child.pid)` (`MEMBER_CONTINUITY_CHANGED`), or `rootGroupProof` hits a zombie root with a live member (`LEADER_UNPROVEN`, `:172-176`). Under load, D ≥ 250 ms makes this ordering likely.
- **Class (a)/(b):** the status (1) and the cleanup are correct either way. Only the error class and `observationFailure` change with scheduling. The test asserts the class (`:58-59`), which assumes `exit` is processed before any later poll.

## 3. phase-e-runner: `rejects zero executed tests…` (a)/(b) the child exits before the root identity is pinned
- **Assertion:** `src/test/phase-e-runner.test.ts:163` expects `'executed'` and receives `Phase E child failed: assignments (exit 1): Owned resource observation failed` (verified, log :1271-1277).
- **Race (strong inference, `sql-report.json` not preserved):** the fake vitest (`:161`) writes one file and exits 0. It has no descendants and sends no IPC, the deadline never fires, and `ps` errors are ruled out. That leaves the spawn handler (`:240-258`) as the only producer. If the child is already a zombie when `ps -p`/`ps eww` runs, `:244` takes the `initialRootExit` path (`:252-255`). `preserveChildFailure` covers only `status > 0` (`:339`), so exit 0 becomes status 1. The identity of the failing assertion moves between runs because every fast-exit fake in this file can hit the same race. This is consistent with the Codex note in QA-PK-OBS-1.

## Fixes: make them deterministic, keep the defect classes, no retries
1. **`:204-205`**: if `!actualLeader && observedProcessExit(leader.pid)` (absent or zombie), treat the sample as retired. Return without updating the lease, keep `previous.commandHash`, and grant no new authority. Keep throwing for a live but unprovable or changed leader. The `changed-leader` and `outside-group` tests still catch that case.
2. **`:214`/`:269`**: at the start of the snapshot, if `observedProcessExit(child.pid)` returns `zombie` or `absent`, skip the snapshot and let the `exit` path (`:276-338`) do the proven cleanup. Our own unreaped child cannot have its PID reused while it is a zombie.
3. **`:150`/`:240`**: gate the start of the child until `rootLease` is pinned, for example with an `--import` gate that waits on the existing IPC channel for `owned-root-pinned`. Keep the fail-closed behaviour on an unobservable root, covered by a dedicated injected test.
4. **Tests:** add a deterministic RED test for each race in the style of `src/test/fixtures/phase-e-retirement-boundary.mjs` and `departed-member` (test `:117`). A `spawnSync` hook synchronously forces the exit at the exact boundary: group SIGKILL plus a wait for the leader zombie after the worker's identity `ps`; root exit plus a wait for the zombie before the next snapshot; a fake that exits immediately plus a 200 ms delay on the first `ps`. Each should fail 100% on the current code with no load, and pass after its fix.

## Decisive experiment (not run)
Use a scratch copy of the runner with env-gated tracing: hrtime start and end for each snapshot and each `ps` call (argv, status, stat), the throw site and reason, and the time of the supervisor's `exit`. The fixtures record hrtime right before `process.kill(-resource.pid)` (process `:113`) and `process.exit` (root-group `:28`). Run each single file 50 times at 0, ncpu and 2×ncpu busy-loop workers, for example `node -e 'for(;;);'` × k (`vitest run <file> --reporter=json`, `--pool=forks --maxWorkers=1`).
- **Confirms:** every failure has its kill or exit timestamp inside the predicted window: between the worker's identity `ps` and the leader `ps` (1), between root death and `exit` with a snapshot in between (2), and child exit before the spawn handler's `ps` completed (3). The failure rate tracks D/250 ms, and no `ps` call takes longer than 2 s.
- **Refutes:** failures outside those windows, or with D ≪ 250 ms.
