# Owner AI Manager — reasoning backend

Jose's latest direction is to build the intelligence of the Owner AI Manager as a conversational bot; Claude owns the chat design. This increment follows that direction rather than starting the previously suggested business-action executor. The already approved operations-partner direction remains the source of product intent. Base: `8d9487362d7f2295dc99f173ebe3977e049719b7`, published on `AI-owner`.

## Goal and approach

Strengthen the existing agent rather than create another chat service. Give it an explicitly configured route to Neon's broader model catalog and a bounded, evidence-checked decision tool. Reuse private approved goals/tasks, current operational tools, canonical jointly checked staffing plans and the existing request lifecycle. A structured recommendation compares options, cites retrieved observations, identifies uncertainty, recommends a next step and states how to check its outcome. It is a concise business decision record, never a request for or display of hidden chain of thought.

Alternatives considered: a prompt-only change does not solve the protocol mismatch or check references; replacing the orchestration with a new agent framework would duplicate authority/recovery and add dependencies. Engineering selects an incremental provider adapter plus a local decision checker. These implementation choices are engineering's calls, not a claim Jose selected a vendor/model or enabled paid usage. His repeated proceed instructions and explicit request to make the intelligence authorize this work without another design-approval cycle.

## Required behavior

1. Keep the existing Responses route as the default. An explicit `NEVORA_OWNER_ADVISOR_API_STYLE=chat_completions` selects Neon's `/v1/chat/completions` (or OpenAI's equivalent). Omitted style means `responses`; unsupported values fail closed. No inferred routing from a model name. The intended branch's actual model availability/capabilities still require a separately authorized live evaluation.
2. Permit an explicit `NEVORA_OWNER_ADVISOR_REASONING_EFFORT=low|medium|high` on Responses only. Omitted means the provider default. Reject that setting on chat rather than send vendor-specific unsupported parameters. Preserve existing activation/data approval/host/key/daily-limit requirements. No environment file, hosted configuration or credential changes.
3. Normalize bounded Chat Completions text/content blocks and function calls into the current loop. Retain valid tool-call/result pairing and existing stateless encrypted Responses reasoning continuation. Reject incomplete/refused/unknown content, invalid roles, excessive choices/items and malformed call identities before executing tools. Chat requests omit `parallel_tool_calls` because some catalog models reject it; any returned calls execute sequentially under the same limits. No fallback to another model/provider, retry or extra paid critic call.
4. Keep six provider turns, eight total tool/review slots (including mandatory briefing), 20-second provider calls, 60-second investigation, 131072-byte response streams, 48000-character individual tool context and 12000-character public answers. Add a 262144-character aggregate request-body cap. These are bounds, not dollar-budget or hosted latency guarantees.
5. Assign fresh, investigation-local evidence IDs `E1`…`E8` only to actual completed operational reads. Include observation time, tool scope and partial status with the data. Saved priorities/goals are explicit Owner intent; notes and prior answers are dated claims, not current facts, policy or action consent. No evidence ID can reference another request, unperformed tool or model-created source.
6. Add local `review_decision`: strict bounded summary, observations with evidence references, separate options/tradeoffs, one recommended option or an explicit missing-decision case, uncertainty, next step and outcome check. Optional coverage references bind one option to exactly one actual canonical alternative by evidence ID/index. Unknown references, mixed alternatives within one option, missing partial-data acknowledgement or fabricated plan indexes produce bounded correction feedback. At most two decision-review attempts; existing overall slots/turns still apply. Once the model submits a decision, raw prose cannot bypass a failed check.
7. Accepted decisions render through the existing `answer.text` and server-owned `sources`/workflow evidence; do not add chat controls, styles or require a new client. Server-owned partial/coverage/payroll caveats accompany the decision. Simple answers and necessary clarifying questions can retain plain prose. Structural/reference checks are not semantic truth verification: the model can still misinterpret evidence. Tests using fictional provider transcripts prove orchestration/contracts, not live model judgment or “extreme intelligence.”
