# Private workforce worker operations

This is a prepared backend operating packet. No Linux host, service, timer, alert sink or new hosted reader credential was installed or enabled. The only actual worker/provider acceptance remains the source-qualified receipts linked below. Native apps and native dispatch are excluded; the notification commands here are Web Push. Current staging remains closed.

## Scope, authority and cost
The existing payroll and Web Push services own scheduling, business-key deduplication, claims, retries, final authorization, leases and partial outcomes. The new private supervisor selects only payroll, notifications-dispatch or notifications-reminders. It invokes those original entrypoints without a shell, bounds the owned process group and records invocation status. CLI exit0 proves a completed invocation; it does not prove jobs existed, payroll approval, delivery, inbox/device receipt, legal readiness or exactly-once external effects.

Use an approved existing private host; no new Render/paid service is required by the source. Host selection, Node24 path, service account, credential custody, schedule/capacity, thresholds, named responder, existing alert destination and actual operating acceptance are still unset. The examples support multiple configured companies on one host, with one canonical private state directory and exactly one instance per company/environment/command. Never run the same scope/command under another state folder to evade its lock. No resource has been purchased.

Operations enablement is separate from original payroll, notification feature/delivery/test and commerce flags. Keep all off until the target is approved. Monitor only explicitly configured commands; an optional disabled payroll module is not a prerequisite for notification health. The supplied60second cadence/600second thresholds are proposals, not approved SLAs.

## Source and private configuration
Pin a reviewed commit and exact lockfile on the selected host; install the approved Node24 runtime/dependencies. Stop/drain workers before changing a checkout or source label. NEVORA_OPERATIONS_SOURCE_SHA is an operator-declared identity in receipts, not independent cryptographic proof of deployed bytes. The final build/custody receipt and host checkout verification establish source provenance. Do not reuse a successful heartbeat from another source, company or environment.

Use only the curated ops/workforce/worker.env.example fields. Store sensitive values in the approved secret store, projected into an operator-owned0600 environment file at the selected host; never put them in Git, Jira, CLI arguments, chat or stdout. Do not copy the web/provisioner environment. Explicitly omit the Owner/browser NEVORA_WORKSPACE_TOKEN_SECRET and APP commerce NEVORA_COMMERCE_BINDING_KEY; machine routing rejects either, including empty values. Management/bootstrap/Stripe/SMTP credentials do not belong here. Web Push delivery material is separately approved provider custody, not supplied by this packet.

The state directory must already exist, be canonical/absolute with no symlink, owned by the service UID and0700. Receipts/locks are0600. Both scopes require isolated routing; supervised commands cannot fall back to DATABASE_URL/single_company. The child receives the exact expected company/environment and checks its actual current WORKER binding before any business operation.

## Dedicated routing reader setup gate
Prepare one fresh restricted LOGIN role named by workerControlRole(companyUUID, test|production): nv_control_worker_t_<32 UUID hex> or nv_control_worker_p_<32 UUID hex>. An approved operator creates its password directly into the exact approved store. Do not create or distribute it until that runtime destination and scope are authorized. No password is generated or returned by configureWorkerControlReader.

On an acquired operator PoolClient, configureWorkerControlReader(client, role) verifies restricted flags, no memberships/object ownership or broad relation access, then transactionally creates security-barrier views and grants only their SELECT plus schema usage. It refuses an existing elevated/broad principal rather than silently repurposing it. The fixed views bind session_user to its company UUID/environment and return only active current WORKER custody. Base registry/secrets, APP ciphertext, another company/environment, inactive history and APP/BOOTSTRAP resolution remain unavailable. No hosted setup was performed; these checks were executed only in discarded owned PostgreSQL.

The reader URL must use its exact role, approved control database, password and verify-full TLS for Neon; production cannot use loopback. Local loopback is admitted only for owned test environments. Give the worker only the routing encryption key and its WORKER commerce binding key, never an Owner envelope key. Existing unscoped workers retain their previous contract; this reader is required for the new supervised machine path.

## Invocation and observation
From the pinned repository, run npm run operations:worker -- --help. A configured private invocation uses npm run operations:worker -- run COMMAND; health uses npm run operations:worker -- health COMMAND. Both accept only the three fixed command names. Health is SELECT/file-read only, uses current WORKER authority before/after SQL,5second observation cancellation and a10second standalone watchdog, and reports nonzero on unavailable/unhealthy state. It never claims/sends/completes work or reads employee credentials/payloads.

Health reports exact queue-record counters, expired leases and oldest due age; it excludes future, expired/cancelled and other-environment notifications. Intent and delivery counters are separate records and may describe related work, not distinct people or extra sends. Payroll failures persist until canonical reviewed recovery. Notification failed/expired-lease counts refer to still-live source/delivery records. A missing/corrupt/future/stale/misbound receipt or unconfirmed cleanup is unhealthy. A failed attempt does not erase its earlier last-success timestamp or become success.

Templates in ops/workforce/systemd end in.example and are not installed units. After explicit target authorization, adapt the Node/release/env paths and copy only approved instances under their real unit names; verify with the target host's systemd-analyze verify before installation. Worker oneshots use TimeoutStartSec330, not RuntimeMaxSec, plus cgroup cleanup; health uses20. One timer does not start another copy of its already-active service. The canonical state folder remains shared by the same company's commands. Linux behavior was checked against upstream systemd documentation, but no Linux/systemd execution was performed on this Mac.

## Pause, crash, recovery and rollback
1. Pause the selected timers and stop/drain the exact company worker units before changing configuration, restoring data or removing a stale lock. Confirm the service/cgroup and owned child processes have stopped; a numeric PID alone is not sufficient because PIDs can be reused. Preserve the sanitized receipt and relevant private canonical job status. Do not kill unrelated processes or another agent's work.
2. An ordinary timeout/interruption stops and observes the owned group before releasing its lock. If termination cannot be confirmed, the receipt is failed/cleanupConfirmed=false and the lock remains. SIGKILL/host loss may leave a running receipt/lock and ambiguous external effects. Health flags that state. Do not automatically delete locks or infer rollback from a lost response.
3. After scheduler pause and actual process-custody verification, an authorized operator may archive/remove only that exact stale lock in its configured private state directory. Keep the receipt/history. Restart only the same approved scope/source command; canonical expired leases and business keys recover work. Never reset attempts/leases or mark jobs successful with ad-hoc SQL. Payroll RETRY_JOB remains the existing current-Owner/grant/operation-checked recovery command. Provider-accepted or unknown delivery is not a confirmed failure to resend.
4. For source rollback, pause/drain, retain current immutable database/history, restore the last reviewed compatible source/environment and verify identity/grants before restart. Never down-migrate, recreate a company, reset known credentials or revive old sessions/proofs to make a rollback look successful. A source change starts fresh source-qualified heartbeat evidence.
5. For an incident, keep the exact scope/source/role/receipt/queue-age/timestamps in the private record, notify only the previously authorized responder/sink, and inspect canonical status before retry. This packet sent no alerts and invents no responder. The launch gate requires an observed missing-heartbeat/failed-job/age alarm and its recovery on the actual selected sink.
