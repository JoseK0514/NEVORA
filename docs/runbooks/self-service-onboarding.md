# Self-service onboarding operations

This packet covers the backend in the approved isolated-company design. It is not production authorization, UI certification, hosted Neon evidence or a promise of inbox delivery. Existing customers remain on their current `single_company` deployments. Never flip one to isolated mode, apply the fresh-company seed chain to an existing database, copy an existing customer's branch, or drop a database as compensation.

## Enablement and principals

Use a separate isolated deployment with reviewed wildcard company routing/TLS and a configured signup origin. Apply control migrations0001–0005 in recorded order with an operator principal. Fresh company schema uses the exact generated canonical manifest, including the0055 tail and distinct0046 Owner-memory append, plus the existing FINAL chain; held Phase F migrations remain held. An upgrade/restore must apply only verified missing additive migrations from the approved source, while suspended. Never rerun the full seed/bootstrap chain against existing data or rewrite an immutable initial bootstrap receipt.

The web service receives only its restricted control principal, onboarding/signup encryption/signature keys and normal application configuration. It never receives the Neon management key, provisioner control credential or privileged bootstrap URL. The separate provisioner receives its own restricted control principal, explicitly approved account/region/resource policy, management key and positive new-project allowance. Fresh restricted control role grants are generated by `src/lib/onboarding/control-principals.server.ts`; create the approved generated role names with LOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOINHERIT, NOBYPASSRLS, NOREPLICATION, no memberships and no object ownership. Verify actual grants/flags/denials in the selected hosted environment before enabling. Do not apply a grant template to an unreviewed reused/elevated role.

`NEVORA_ONBOARDING_ENABLED`, provider enablement, provisioner-worker enablement and invitation delivery are separate explicit flags, all off by default. `NEVORA_ONBOARDING_MAX_NEW_PROJECTS_PER_DAY=0` prevents creation. Resource policy must set positive bounded compute, suspend, history and all provider quota fields; zero/unlimited quota values reject. Configure reviewed current terms/privacy versions and verify the published pages before opening signup. No analytics/replay is introduced by this work.

Inspect `.env.example` and the configuration readers for the exact variables; keep secrets in the approved secret store, never the browser, Git, Jira, commands or logs. The three32byte keys must be distinct. Set region/account/policy/operator/environment explicitly. Run the disabled worker/operator commands first and observe `disabled`; configuration is not authentication, a successful local test is not hosted validation, and a deployment record is not release approval.

Remote SMTP in the onboarding test environment also requires NEVORA_STAGING_EMAIL_RECIPIENT, set to the explicitly approved mailbox. The shared verification/invitation/recovery transport refuses another recipient before opening SMTP. Missing/invalid configuration reports unavailable delivery; a blocked recipient is a definite failure, never an unknown provider outcome. Local owned SMTP remains available without real-network credentials.

## Runtime and recovery

`npm run onboarding:worker` executes one bounded private invocation. Schedule it only after the hosted controls are verified. It performs bounded expired-proof maintenance, claims durable provisioning work, or processes pending first-Owner grant/finalization work. Keep account resource/cost alerts, lease heartbeat/failure alerts and per-company migration monitoring connected to an actual observed sink before enabling. Never log email proofs, redirects, passwords, connection strings, encrypted private payloads or management keys.

Public recovery repeats the original operation and body under current signup/Owner authority. A lost create response waits for exact account/region/name/time/project/branch/endpoint reconciliation. UNKNOWN create attempts never POST again automatically. Only a known429 rejection allows the bounded retry. Foreign/ambiguous resources quarantine without company mutation. Source-manifest mismatch must use the original approved worker artifact or a reviewed migration/reconciliation; never edit the recorded source hash to force a resume. Inspect orphan resources by exact immutable ownership and cost policy; do not automatically adopt or delete them.

First-Owner grants expire after15minutes and are distinct from invitations. Activation writes the credential once, consumes the grant and records its immutable receipt, then private finalization activates the company anchor before the registry. The gap fails closed. Recovery uses that original receipt and normal sign-in, without resetting a known password or assuming a browser cookie arrived. No reusable Owner password is stored in control records.

Invitation batches issue at most five of up to50 explicitly reviewed targets per POST. Repeating the same approved command continues only PREPARED targets. UNKNOWN is a pre-dispatch fence and never retries automatically, including after a process crash. GET is read/reconciliation only. Existing168hour validity, revocation, issue limits and proof cleanup remain authoritative. PROVIDER_ACCEPTED means the provider accepted the message, not inbox receipt. A resend requires a new reviewed operation and current target/invitation versions.

## Retention and maintenance

Registration expiry is configured by retention days; renewed verification can resume unfinished business provisioning. Business provenance, immutable operation tombstones, runtime credentials and company records are separate retention classes, not an assertion that all business data is erased after signup expiry. Review their legal/security retention and deletion policy before public enablement.

Private maintenance retires encrypted verification delivery/session-claim and initial-Owner redirect bearers at least24hours after expiry, clears expired verification digests, and removes bounded old admission counters. It preserves operation IDs, current material and business provenance, never retries delivery and never deletes provider resources. The initial grant ciphertext can only be erased one way after terminal expiry. Existing invitation digest maintenance preserves history. Run maintenance periodically through the enabled provisioner, or explicitly with a separate operator principal:

- Set `NEVORA_ONBOARDING_OPERATOR_MODE=maintenance` and an approved `NEVORA_OPERATOR_CONTROL_DATABASE_URL` for the same control database with a different username from the web principal.
- Run `npm run onboarding:operator -- cleanup` in the selected environment. It reports counts only, up to100 records per class per invocation.
- Observe repeat calls converge to zero while current material remains intact. Maintenance does not enable new signup or provider creation.

## Suspension, backup and restore

A restore is a separate operator action requiring current backup provenance, an approved source/environment, an actual business-owner recovery/identity review and the required release authority. None has been performed against hosted/customer data here.

1. Disable new work for the affected company and stop/drain its workers and in-flight external deliveries. Record the control revision/incarnation, project, source manifest and backup custody. Keep the existing resource; never delete/recreate it as a retry.
2. With `NEVORA_ONBOARDING_OPERATOR_MODE=restore` and a separate approved operator control principal, run `npm run onboarding:operator -- status WORKSPACE_UUID`, then `... -- suspend WORKSPACE_UUID EXPECTED_REVISION`. Inspect status after a lost suspension acknowledgement. Registry suspension denies new bindings; draining and the company anchor lock close in-flight work before restoring.
3. Restore only the verified matching company image into its exact owned project/database, and apply only verified missing additive migrations. Keep the registry suspended throughout. Check actual project/database/provisioner identity and backup source; never restore one customer's image into another company.
4. Choose one operation UUID and retain it. Run `npm run onboarding:operator -- retire-restored WORKSPACE_UUID FROM_INCARNATION ORIGINAL_OPERATION_UUID`. A lost company/control commit response repeats that same operation. The immutable company receipt prevents a second credential rotation. This command does not activate the company.
5. Retirement increments the incarnation once, clears sessions/recovery/passkey/native challenges, revokes restored passkeys and invitations/grants, invalidates Clocker device/session credentials, detaches Web Push/native private material, cancels pending push work and fails old payroll jobs for review. Restored passwords are replaced by an unknown random credential; recovery uses the existing verified/assisted recovery process. Old runtime login roles and secret references are disabled. Business profiles, settings, audit history and operational data are retained.
6. Keep SUSPENDED. Re-verify the current Owner and registered recovery channel; review restored employee/contact/payroll facts, queued work, Clocker PIN history and device enrollment, since a backup may predate later changes. PIN history is preserved; reissue PINs through the existing Owner-audited commands before enrolling replacement devices. Never revive restored native consent/token material or queued deliveries. Obtain fresh consent/registration where required.
7. A separately reviewed reactivation creates fresh restricted APP/WORKER logins and encrypted secret references for the new incarnation, verifies exact permissions, anchor/registry/project/source equality and current business identity, then activates anchor before registry. Old secrets/roles/envelopes must remain unusable. This packet intentionally provides no automatic reactivation command. Record hosted tests, source mapping, QA/security/UI dispositions and Jose's actual release authorization before reopening.

Owned local tests exercise real `pg_dump`/`pg_restore`, retirement, wrong-company refusal and lost acknowledgements. Hosted backup/PITR, role capability/entitlement, email, DNS/TLS and observed recovery remain distinct gates.

## Acceptance and rollback

From a clean committed source, run `node scripts/onboarding-acceptance.mjs` with the reviewed PostgreSQL server/client binaries. It refuses existing application/test targets, creates only invocation-owned loopback databases, runs both foundation- and exchange-prefixed Company Access suites and writes a source/tree-bound backend report with full logs. The report explicitly records UI/hosted/production as unverified. CI adds `onboarding-backend` without replacing existing mandatory gates. Hosted CI status and branch protection must be verified, not inferred from YAML.

Also run the root suite, typecheck, lint, source-bound production build and applicable existing CI/regression checks. Keep every failure/skip and independent finding visible. Preserve evidence outside tracked application source. An absent Claude onboarding surface cannot be tested as a finished UI; do not substitute a fake wizard or count HTTP tests as browser acceptance.

Rollback disables new signup/provider work and pauses affected jobs; existing active company access remains independent. Preserve durable operations/resources and reconcile unknown outcomes under the recorded source. Never force-reset credentials, clear business data, drop projects or publish production to make a rollback appear successful.

### Post-review backend controls

Reservation throttling and provider dispatch are separate: an account-wide UTC-day lock journals the dispatch slot with its attempt before POST. Pending/unknown/accepted attempts occupy a slot; only a confirmed rejection releases it. Backlogs and lowering a nonzero cap do not bypass the dispatch ceiling. No unknown create is automatically repeated.

Company WORKER capabilities are enumerated in `worker-privileges.ts`; credentials, session creation and employee role/profile writes are denied. Fixed source-table lock functions and checked, immutable non-authority lock columns preserve existing job lock protocols without granting those writes. Hosted role capabilities must be checked from the actual deployed candidate; existing runtime roles are not silently upgraded by local bootstrap changes. Defaults remain disabled.
