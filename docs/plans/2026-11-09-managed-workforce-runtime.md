## Chosen implementation

The existing one-shot supervisor/health CLI and durable PostgreSQL queues remain canonical. Add a bounded managed-host controller, not another queue engine. Use one small Node service and 1 GB durable state disk, with sequential scoped commands and no autoscaling. Current official Render references identify `0.5c-512mb` / legacy `starter`, with published $7/month compute and $0.25/GB/month disk pricing. Verify the actual proposed service estimate fits the $10 ceiling before creation; no Redis, database, workspace upgrade or extra paid service is included.

Use a dedicated health-only web service for the worker process: Render background workers have no inbound health endpoint, and a separate observer must detect host loss. Public `/ready` reveals only process readiness; the fixed health-observation route requires a fresh HMAC request and returns bounded aggregate status, never credentials, employee data, arbitrary selectors or command execution. An independent Neon Function polls that exact HTTPS origin. It holds only a restricted aggregate incident-journal database principal and mail-provider custody; the worker never receives SMTP, Stripe, APP/browser roots or management credentials. Mail is fixed to the approved support destination, staged off until test approval.

The controller supports a finite operator-supplied set of company/environment profiles in a private managed secret. Profiles are validated against a strict allowed environment-variable set and the current company-scoped WORKER reader. No global process.env mutation chooses a tenant: each canonical CLI invocation receives its own curated environment. State directories are derived canonically per company/environment under one private mounted root, with 0700/0600 permissions and no symlink adoption. Source SHA must match trusted deployed source identity.

Render's disk documentation explicitly forbids changing the default shutdown delay for disk-backed services. Design for **30 seconds**, not the 300-second setting available without a disk: stop dispatching immediately, forward SIGTERM to the canonical CLI, wait for bounded owned cleanup, and keep unconfirmed locks for explicit operator recovery. Never automatically remove a stale lock or reset a durable business job. The platform's disk rollout stops the old instance before starting the new one; source/credential rotation still requires a drained scope.
