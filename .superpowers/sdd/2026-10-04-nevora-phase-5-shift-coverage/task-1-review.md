## Issues

### Important (Should Fix)

1. **Revalidate session expiry after the profile row lock.** `src/lib/data/shift-change-policy.ts:67` builds the transaction as all `ownerGuards` first, then `SELECT ... employee_scheduling_settings ... FOR UPDATE`, then the profile update. The expiry check is inside `ownerGuards` at line 12. A valid but soon-expiring Owner session can pass that check, wait on another transaction holding the target settings row, expire during the wait, and still write the profile when the lock becomes available. Session/account SHARE locks prevent a competing revocation or role update, but they do not stop wall-clock expiry. This is reachable through the existing hour-target upsert, which locks the settings row without taking the workspace lock (`src/lib/data/schedule-health.ts:156`). Acquire all required mutation locks before the final authority check, or put the current-session predicate in the guarded final update. Add one focused disposable SQL regression that blocks the target settings row, lets the specific session expire while the profile writer waits, then asserts invalid authorization and an unchanged profile/revision. The existing test at `src/test/integration/shift-change-policy.integration.ts:31` only blocks the earlier workspace lock, so it does not answer this case.

2. **Preserve target location and owning week in legacy swap history.** `db/migrations/0010_shift_coverage_automation.sql:145` imports `target_terms` with only `to_jsonb(t)` from the target `shifts` row. The source snapshot immediately above it joins its schedule and records `locationId`/`weekStart`, but the target snapshot does neither. A cross-location/cross-week legacy swap therefore retains only the target's schedule ID; when that mutable shift/schedule is removed, the event cannot recover the target location or owning week. Those are explicit `ShiftTerms` facts (`src/lib/shift-changes/types.ts:23`) and part of the durable original-terms requirement. Join the target schedule when backfilling target terms and preserve its location/week (and the unknown-consent labeling consistently). Add an upgrade fixture with a legacy swap across different locations/weeks, delete the live target/schedule, and verify both event snapshots still retain their respective material terms. The current upgrade/history fixtures use only coverage (`src/test/integration/shift-change-schema.integration.ts:12`), so this omission is untested.
